2nd-brain · user flow

사람은 큐레이션,
에이전트는 컴파일

LLM Wiki는 자동 지식 생성기가 아니에요. 사람이 자료를 고르고 방향을 정하면, 에이전트가 요약·연결·정리·검증을 맡는 분업 구조입니다. 아래는 한 자료가 위키에 들어와 재사용되기까지의 전체 흐름이에요.

사람 (curator · director) 에이전트 (summarize · link · file · verify)

한 자료의 라이프사이클

1
발견 & 캡처 capture
사람

흥미로운 글·영상·논문 발견 → “이거 위키에 넣어줘”

에이전트

원본을 raw/에 저장 + 출처·해시 기록. 이후 절대 수정 안 함(immutable).

2
컴파일 compile
사람

개입 없음 — 방향만 줬으면 맡겨둠

에이전트

소스 읽고 canonical 페이지 합성, [[링크]]·태그·출처 부착, index/log 갱신

3
검토 & 승인 review
사람

결과 확인, confidence·모순 플래그 점검, 개인 해석 추가 후 승인

에이전트

낮은 신뢰도·모순 페이지를 리뷰용으로 표면화

4
질문 = 재사용 query
사람

도메인 질문을 던짐 (몇 주 뒤라도)

에이전트

원본 재검색 없이 위키에서 즉답. “[[page-a]]와 [[page-b]] 기준…”

5
파일링 = 복리 file
사람

“이 답변 저장해둬” (다시 만들기 아까운 것만)

에이전트

가치 있는 답변을 queries/에 저장 → 다음 질문의 재료가 됨

답변이 다시 위키가 되어 지식이 쌓인다 (2단계로 환류)
6
유지보수 lint
사람

주기적으로 “위키 점검해줘”

에이전트

고립 페이지·깨진 링크·오래된 내용·모순을 리포트

왜 이렇게 나누나

사람 = 판단, 에이전트 = 노동

무엇이 중요한지, 무엇을 믿을지는 사람만 안다. 요약·교차참조·일관성 유지·검증 같은 반복 노동은 에이전트가 지치지 않고 한다. 이 경계가 흐려지면 위키는 중복 페이지 더미로 퇴화한다 — 그래서 SCHEMA.md라는 계약이 에이전트의 자유를 제한하는 것.

이 플로우의 2단계(컴파일) 내부 동작은 “LLM Wiki 컴파일 = 빌드 파이프라인” 문서에서 next build / mvn package 비유로 자세히 다룬다.
