# 보험 인수심사 도메인 적용

## 1. 요약

이 저장소의 스키마를 **보험 인수심사(underwriting) 지식베이스**로 전환할 수 있는지 검토한 결과, **구조적으로 가능하며 오히려 적합도가 높다**고 판단한다.

근거는 두 가지다. 첫째, 스키마가 특정 도메인에 종속되지 않도록 설계되어 있다. 둘째, 이 스키마가 강제하는 **출처 추적, 상충 기록, 불변 이력**이 인수심사 업무가 원래 요구하는 것과 정확히 대응한다.

다만 실행 전에 반드시 해결해야 할 제약이 있다. **개인 건강정보 취급 금지 규칙을 스키마에 먼저 명문화**하지 않으면 이 저장소를 인수심사 업무에 사용해서는 안 된다.

## 2. 배경과 문제

인수심사 지식은 현재 여러 형태로 흩어져 있다.

- 사내 인수지침서(개정 시마다 판본이 갈림)
- 재보험사 인수 매뉴얼
- 상품별 약관과 상품요약서
- 의학 문헌과 통계(예후, 사망률)
- 감독기관 공시, 분쟁조정례, 판례
- 담당자 개인의 경험적 판단

문제는 **"이 인수 판단의 근거가 무엇이었는가"를 나중에 재현하기 어렵다는 점**이다. 지침은 개정되고, 회사·재보험사마다 기준이 다르며, 관행적 판단과 문서화된 기준이 섞인다. 민원이나 분쟁이 발생했을 때 "당시 기준으로는 이러했다"를 입증하기 위한 추적 가능한 구조가 필요하다.

## 3. 목표와 비목표

**목표**

- 인수심사 **근거 지식**을 출처 추적이 가능한 형태로 축적한다.
- 회사별·재보험사별 기준 차이와 상충을 숨기지 않고 명시적으로 기록한다.
- 지침 개정 이력을 보존해 특정 시점의 판단 근거를 재현할 수 있게 한다.

**비목표**

- **인수 판정 자동화가 아니다.** 이 위키는 근거 참조용이며, 승낙·거절·할증 결정은 사람과 공식 UW 시스템의 몫이다.
- **개별 청약 건 관리 시스템이 아니다.** 실제 피보험자 정보는 이 저장소에 들어가지 않는다.
- 기존 UW 시스템이나 계약관리 시스템을 대체하지 않는다.

## 4. 제안 내용

### 4.1 도메인 중립성 근거

이 템플릿은 PKM 전용이 아니다. [SCHEMA.md](../../SCHEMA.md)에 명시적 근거가 있다.

- `SCHEMA.md:67` — *"Add only tags that fit **the chosen wiki domain**; do not seed domain tags here."* 도메인은 사용자가 선택하는 값으로 정의되어 있다.
- `SCHEMA.md:21` — *"Zero canonical pages is a valid wiki state. The initial repository deliberately contains no raw source record and no canonical page."* 현재 들어 있는 8개 정본 페이지는 데모 콘텐츠다.

즉 태그 택소노미와 콘텐츠를 교체하면 도메인 전환이 성립한다.

### 4.2 스키마 기능과 인수심사 요구의 대응

이 스키마의 까다로운 제약들이 인수심사에서는 그대로 실무적 이점이 된다.

| 스키마 기능 | 인수심사에서의 의미 |
| --- | --- |
| `sources` 경로 강제 + `^[raw/...]` 클레임 마커 | 인수기준의 근거가 어느 지침 어느 부분인지 **문장 단위로 역추적**. 민원·분쟁·감독 대응의 기반 |
| `contested: true` + `contradictions` | 회사별·재보험사별 기준이 **상충하는 것이 정상**. 이를 은폐하지 않고 구조적으로 기록 |
| `confidence: high/medium/low` | 복수 근거(지침 + 의학문헌)로 뒷받침되는 기준과 관행적 판단을 구분 |
| `raw/` 불변성 + `_archive/` | 지침은 수시 개정된다. **"2026년 3월 청약 건은 당시 기준으로 판단했다"**를 재현 가능 |
| `log.md` append-only | 지식 변경 이력이 곧 **감사 추적(audit trail)** |
| Zotero 연동 | 인수심사는 **의학 문헌 의존도가 높다.** 서지 관리 파이프라인이 이미 갖춰져 있음 |

특히 마지막 두 항목은 공개된 다른 LLM Wiki 구현체에는 없는 이 템플릿 고유의 강점이다.

### 4.3 디렉토리 매핑안

```text
raw/                     # 불변 원본
├── guidelines/          # (신규) 사내 인수지침서, 상품요약서, 약관 발췌
├── papers/              # 의학 논문 (Zotero 연동) — 예후·사망률 통계
├── articles/            # 업계 자료, 해설 기사
└── web/                 # 감독기관 공시, 보험개발원 자료, 분쟁조정례

entities/                # 보험사, 재보험사, 상품, 감독기관, UW 시스템
concepts/                # 역선택, 도덕적 해이, 표준체/우량체, 할증·부담보·거절,
                         # 고지의무 위반, 예정위험률, 손해율, 계약 전 알릴 의무
comparisons/             # 간편심사 vs 완전심사 / 유병자보험 vs 표준체 /
                         # 회사별 특정 질환 인수기준 비교
queries/                 # "HbA1c 7.5 + 합병증 없음 → 인수 가능 범위는?"
                         # "고혈압 병력 3년, 약물 조절 양호 시 할증 근거는?"
```

`comparisons/`와 `queries/`가 인수심사에서 활용도가 가장 높을 것으로 예상한다. 기준 비교와 구체적 사례 질의가 실무의 중심이기 때문이다.

### 4.4 태그 택소노미 교체안

현재 등록된 9개 태그(`pkm`, `notebooklm`, `knowledge-graph` 등)는 데모용이므로 교체한다. 초안은 다음과 같다.

- `underwriting`: 인수심사 일반 기준과 절차
- `medical-uw`: 의학적 인수심사
- `financial-uw`: 재정적 인수심사
- `risk-assessment`: 위험 평가와 등급 산정
- `reinsurance`: 재보험사 기준과 특약
- `regulation`: 감독규정, 법령, 분쟁조정례
- `product`: 상품 구조와 약관
- `claims`: 지급 심사와의 접점

`SCHEMA.md`의 태그 등록 절차에 따라 **사용 전에 먼저 등록**해야 한다.

## 5. 리스크와 제약

구조는 맞지만, 보험 도메인 특성상 그대로 사용하면 안 되는 지점이 있다. **아래 1번은 다른 모든 항목보다 우선한다.**

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| **개인 건강정보 유입** | 건강정보는 개인정보보호법상 **민감정보**. Git 이력에 들어가면 파일을 지워도 커밋 히스토리에 영구 잔존한다. | **지식(기준·근거)만 저장하고 개별 청약 건은 절대 넣지 않는다.** 사례가 필요하면 완전 비식별 가공. 이 규칙을 `SCHEMA.md`에 명문화한다. |
| **NotebookLM 외부 전송** | NotebookLM에 사내 인수지침을 올리면 Google 서버로 **사외 반출**이다. `notebooklm-py`는 비공식 API라 위험이 더 크다. | 사내 정보보호·컴플라이언스 승인 필수. 미승인 시 이 단계를 제외하고 Obsidian + 로컬 에이전트 구성만 사용한다. |
| **저작권·영업비밀** | 재보험사 인수 매뉴얼, 약관, 보험개발원 자료는 라이선스 대상 저작물이다. | `raw/`에 전문을 복사하기 전 사내 사용 범위를 확인한다. 필요 시 전문 대신 출처 메타데이터와 인용 범위만 보존한다. |
| **AI 산출물의 인수 판정 사용** | 위키 내용을 승낙·거절 근거로 직접 사용하면 심사 책임 소재가 불분명해진다. | 위키는 **근거 참조용**임을 `SCHEMA.md`에 명시한다. 최종 판정은 사람과 공식 시스템이 수행한다. |
| **지침 개정에 따른 기준 노후화** | 옛 기준을 현행으로 오인하면 잘못된 심사로 이어진다. | 정본 페이지에 **적용 시점**을 필수 기재한다. 개정판은 새 raw 레코드로 캡처하고 구 정본은 `_archive/`로 이동한다. |

## 6. 실행 계획

- [ ] **`SCHEMA.md`에 개인정보 취급 금지 조항 추가** — 다른 작업보다 먼저 수행한다
- [ ] `SCHEMA.md`에 "근거 참조용, 인수 판정 비자동화" 범위 선언 추가
- [ ] 데모 콘텐츠 정리 — 기존 정본 8개와 raw 13개를 제거하거나 `_archive/`로 이동하고 `index.md`·`log.md` 동기화
- [ ] 태그 택소노미를 4.4안으로 교체 등록
- [ ] `raw/guidelines/` 디렉토리를 `SCHEMA.md` 디렉토리 표에 등록하고 인정 파일 형식 정의
- [ ] 지침 개정 관리 규칙 정의 — 적용 시점 표기 방식, 구 판본 보관 절차
- [ ] NotebookLM 사용 여부에 대한 사내 컴플라이언스 확인
- [ ] 파일럿: 단일 질환(예: 당뇨) 범위로 raw 수집 → 정본 컴파일 → 린트까지 1회전 수행

## 7. 미결정 사항

- **데모 콘텐츠 처리 방식** — 완전 삭제할 것인가, `_archive/`로 보존할 것인가, 아니면 별도 브랜치로 분리할 것인가?
- **저장소 분리 여부** — 인수심사용을 이 저장소에서 이어갈 것인가, 별도 저장소로 분리할 것인가? 템플릿 성격을 유지하려면 분리가 유리하다.
- **NotebookLM 사용 가부** — 사내 승인 결과에 따라 워크플로우 구성이 달라진다.
- **공개 범위** — 개인용인가 팀 공용인가. 팀 공용이면 접근 통제와 리뷰 절차가 추가로 필요하다.
- **`owner` 지정** — 스키마 변경과 컴플라이언스 판단의 책임자.
