# 여행·항공 실무 지식베이스

## 1. 요약

항공권 발권 전략, 마일리지·제휴 프로그램, 노선·경유, 비자·입국 요건처럼 **직접 써먹는 여행 지식**을 이 저장소의 스키마로 축적하는 기획이다.

여행 지식은 이 스키마의 강점과 약점이 동시에 극대화되는 도메인이다. 출처가 불분명한 정보가 범람하고 조건부 지식이 많다는 점에서 `sources` 강제와 `contested` 필드가 특히 유효하다. 반면 **정보 휘발성이 매우 높아**, 스키마가 전제하는 "지속형 지식"과 정면으로 충돌한다.

따라서 이 기획의 핵심은 도메인 매핑이 아니라 **신선도(freshness) 관리 장치를 스키마에 추가하는 것**이다. 4.4절의 휘발성 등급과 재검증 주기가 이 문서의 실질적 제안이다.

## 2. 배경과 문제

여행 정보는 이미 인터넷에 넘치지만, 실제로 쓰려고 하면 반복해서 같은 문제에 부딪힌다.

| 문제 | 구체적 양상 |
| --- | --- |
| **낡음** | 마일리지 공제표, 비자 요건, 운항 노선이 수시로 바뀐다. 블로그 글에는 작성일이 없거나 개정 반영이 안 되어 있다. |
| **출처 불명** | 발권 팁 상당수가 전언이다. 항공사 공식 규정인지 누군가의 경험인지 구분되지 않는다. |
| **조건 누락** | "이렇게 하면 된다"는 정보에 국적·체류기간·경유지·발권 채널 같은 **성립 조건이 빠져 있다.** |
| **상충** | 같은 질문에 커뮤니티마다 답이 다르다. 공식 약관과 실제 운영이 다른 경우도 있다. |

매번 검색해서 다시 판단하는 비용이 크고, 그 판단 근거가 남지 않아 다음 여행 때 처음부터 반복한다.

## 3. 목표와 비목표

**목표**

- 반복해서 재사용할 여행 지식을 **성립 조건과 출처가 붙은 형태**로 축적한다.
- 공식 규정과 경험적 관찰을 `confidence`로 명확히 분리한다.
- 정보의 **유효 시점과 재검증 시기**를 구조적으로 관리한다.

**비목표**

- **항공권 가격 추적이 아니다.** 가격은 휘발성이 극단적이라 위키에 담을 대상이 아니다. 담는 것은 "가격이 형성되는 구조"다.
- **개인 여행 일정 관리가 아니다.** 일정·예약은 캘린더와 앱의 몫이다.
- **실시간 운항 조회가 아니다.** 노선의 존재와 구조는 다루되, 당일 운항 상태는 다루지 않는다.
- 법적·행정적 조언이 아니다. 비자와 입국 요건은 항상 공식 출처 재확인이 전제다.

## 4. 제안 내용

### 4.1 정본 디렉토리 매핑

```text
entities/       # 항공사, 얼라이언스(스타·원월드·스카이팀), 공항,
                # 마일리지 프로그램, 호텔 체인, 카드 제휴 프로그램

concepts/       # 예약등급(부킹 클래스), 마일리지 적립·공제 구조,
                # 스톱오버·오픈조, 코드셰어, 유류할증료, 수하물 규정,
                # 환승·최소연결시간(MCT), 트랜짓 비자, 무비자 체류,
                # 노쇼·변경·환불 규정, 운송약관(CoC)의 구조

comparisons/    # 얼라이언스별 특전 비교 / 항공사별 마일리지 공제 비교 /
                # 직항 vs 경유 / 직접 발권 vs OTA / 좌석 등급별 가치

queries/        # "인천→유럽 마일리지 공제가 가장 낮은 경로 조합은?"
                # "일본 경유 시 트랜짓 비자가 필요한 국적 조건은?"
                # "스톱오버를 붙일 수 있는 발권 조건은?"
```

`queries/`가 이 도메인의 중심이 될 가능성이 높다. 여행 지식은 대부분 **"내 조건에서 이게 되나?"** 형태의 질문으로 소비되기 때문이다.

### 4.2 태그 택소노미안

- `airline`: 항공사와 운항 주체
- `alliance`: 얼라이언스와 제휴 관계
- `mileage`: 마일리지 적립·공제·특전 발권
- `fare-rules`: 운임 규정, 예약등급, 변경·환불
- `routing`: 노선, 경유, 환승 구조
- `visa`: 비자와 입국 요건
- `baggage`: 수하물 규정
- `airport`: 공항 시설과 운영

`SCHEMA.md`의 등록 절차에 따라 **사용 전에 먼저 등록**한다.

### 4.3 공개 데이터 소스

여행 도메인은 **1차 공식 출처가 잘 공개되어 있다**는 점이 보험 도메인보다 유리하다.

| 계층 | 소스 | 얻는 것 |
| --- | --- | --- |
| 항공사 공식 | 각 항공사 운송약관(Conditions of Carriage), 마일리지 프로그램 약관, 수하물 규정 페이지 | **1차 규정 원문.** 최우선 근거 |
| 얼라이언스 공식 | 스타얼라이언스·원월드·스카이팀 공식 사이트 | 회원사, 등급 특전, 라운지 정책 |
| 정부 공식 | 외교부 해외안전여행(`0404.go.kr`), 각국 대사관·이민국 | **비자·입국 요건.** 유일하게 신뢰할 출처 |
| 정부 공식 | 국토교통부 항공정보포털(`airportal.go.kr`) | 노선·운항 통계 |
| 공공 데이터 | [공공데이터포털](https://www.data.go.kr/) | 항공 운항·통계 API |
| 공항 | 인천국제공항공사 등 각 공항 공식 | 시설, 환승 절차, 최소연결시간 |
| 오픈 데이터셋 | OpenFlights, Wikidata | 공항·항공사 코드, 노선망 기초 데이터. **라이선스 확인 필요** |
| 커뮤니티 | 항공 관련 포럼·블로그 | 실제 운영 관찰. **`confidence: low` 고정** |

커뮤니티 정보는 배제하지 않는다. 공식 규정과 실제 운영이 다른 지점을 포착하는 유일한 경로이기 때문이다. 다만 **공식 출처와 같은 층에 두지 않고**, `contested: true`와 함께 양쪽 입장을 병기한다.

### 4.4 휘발성 등급과 재검증 주기 — 이 기획의 핵심

여행 정보는 "언제 확인한 정보인가"가 내용만큼 중요하다. 기존 스키마에는 이 개념이 없으므로 다음을 추가할 것을 제안한다.

**raw 레코드 필수 필드 추가**

- `retrieved`: 해당 자료를 실제로 확인한 날짜. 원본의 게시일과 별개로 관리한다.

**정본 페이지 필수 필드 추가**

- `volatility`: `A` / `B` / `C` 중 하나
- `verified`: 마지막으로 내용을 재확인한 날짜

| 등급 | 재검증 주기 | 해당 지식 |
| --- | --- | --- |
| **A (고휘발)** | 1~3개월 | 비자·입국 요건, 운항 노선 개설·단항, 마일리지 공제표 개정, 유류할증료 |
| **B (중휘발)** | 6~12개월 | 마일리지 프로그램 구조, 수하물 규정, 라운지 이용 정책, 예약등급 체계 |
| **C (저휘발)** | 주기 없음 | 공항 코드, 지리·시차, 얼라이언스 구성, 기재 사양, 개념 정의 |

`verified`가 주기를 넘긴 A·B 등급 페이지는 **린트에서 경고 대상**으로 삼는다. 이렇게 하면 "낡은 정보가 조용히 남아 있는" 상태를 구조적으로 막을 수 있다.

등급 A 페이지는 본문 상단에 재확인 안내를 고정한다.

> 이 문서는 `verified` 시점 기준이다. 실제 여행 전 반드시 공식 출처에서 재확인할 것.

## 5. 리스크와 제약

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| **낡은 정보로 인한 실제 피해** | 비자 요건을 잘못 알면 **입국 거부·탑승 거부**로 직결된다. 위키가 오히려 위험 요인이 될 수 있다. | 4.4의 `volatility`·`verified` 도입. A등급 페이지에 재확인 안내 고정. 비자 정보는 정부 공식 출처만 `confidence: high` 허용 |
| **예약 정보 유출** | PNR(예약번호)은 **6자리 + 성(姓)만으로 전체 여정 조회가 가능**하다. 항공권 번호, 여권번호, 마일리지 회원번호도 마찬가지로 민감하다. | 개인 예약·여권·회원 정보는 **어떤 형태로도 저장소에 넣지 않는다.** 사례가 필요하면 완전히 가공한 예시를 쓴다 |
| **전언 정보의 사실화** | 커뮤니티 팁이 공식 규정처럼 굳어지면 위키 전체의 신뢰도가 무너진다. | 커뮤니티 출처는 `confidence: low` 고정, 공식 규정과 충돌 시 `contested: true`로 병기 |
| **약관 원문 재배포** | 항공사 운송약관·마일리지 약관은 저작물이다. 기획 002와 동일한 문제. | [기획 002](002-data-sourcing.md) 5.1절의 저장 방식 결정을 그대로 적용한다 |
| **오픈 데이터셋 라이선스** | OpenFlights 등은 ODbL 계열 라이선스로, 재배포 시 조건이 붙는다. | 사용 전 각 데이터셋 라이선스를 확인하고 출처 표기 요건을 지킨다 |
| **도메인 혼재** | 보험(001·002)과 여행(003)을 **한 저장소에서 운영하면 스키마가 충돌한다.** 6.1절 참조. | 저장소 분리를 기본 방침으로 한다 |

### 5.1 보험 도메인과의 충돌

`SCHEMA.md:67`은 태그를 *"the chosen wiki domain"*에 맞는 것만 등록하도록 규정한다. **도메인은 단수 전제**다. 두 도메인을 한 저장소에 넣으면 다음이 깨진다.

- 태그 택소노미가 두 갈래로 섞여 `index.md`의 탐색 가치가 떨어진다.
- **정본 링크 최소 2개 규칙**이 서로 무관한 두 클러스터를 억지로 연결하게 만들거나, 한쪽이 고립된다.
- 휘발성 관리 요구가 다르다. 보험은 개정이 느리고 여행은 빠르다.

따라서 **여행·항공은 별도 저장소로 분리**하고, 이 템플릿을 다시 클론해 시작하는 것을 권장한다. 기획 문서는 원본 저장소에 함께 두어도 무방하다.

## 6. 실행 계획

**파일럿 범위: 마일리지 특전항공권 발권**

이 범위를 고른 이유는 다음과 같다.

1. **공식 약관이 전면 공개**되어 있어 1차 출처 확보가 쉽다.
2. 공제표·성수기·스톱오버 같은 **개념이 명확히 구조화**되어 `concepts/`로 떨어진다.
3. 항공사·얼라이언스별 차이가 커서 `comparisons/`가 실제로 유용하다.
4. 공식 규정과 실제 발권 경험이 갈리는 지점이 많아 **`contested` 필드를 검증**할 수 있다.
5. 휘발성 A·B가 섞여 있어 4.4의 등급 체계를 시험하기에 적합하다.

- [ ] **저장소 분리 여부 확정** (5.1절) — 분리 시 템플릿 재클론
- [ ] `SCHEMA.md`에 `volatility`·`verified`·`retrieved` 필드 추가 및 린트 규칙 정의
- [ ] `SCHEMA.md`에 예약·여권·회원 정보 저장 금지 조항 추가
- [ ] 태그 택소노미를 4.2안으로 등록
- [ ] 항공사 1~2곳의 마일리지 약관·공제표 수집 → `raw/`
- [ ] 얼라이언스 공식 특전 자료 수집 → `raw/`
- [ ] 커뮤니티 관찰 2~3건 수집 (공식 규정과의 차이 확인용) → `raw/`
- [ ] 정본 컴파일 1회전 — `entities/` 2~3, `concepts/` 3~4, `comparisons/` 1~2, `queries/` 1~2
- [ ] 린트 및 `index.md`·`log.md` 동기화

목표 규모는 **raw 10~15건 → 정본 7~10페이지**다. 정본이 3페이지 미만이면 위키링크 최소 2개 규칙을 만족할 수 없다.

## 7. 미결정 사항

- **저장소 분리 여부** — 5.1절의 권장안을 채택할 것인가. 나머지 작업의 선행 조건이다.
- **`volatility` 필드 도입 방식** — 정본 frontmatter 필수 필드로 넣을 것인가, 태그로 대체할 것인가. 필수 필드가 린트하기 쉽지만 스키마 변경 폭이 크다.
- **대상 항공사 범위** — 국적사만 볼 것인가, 자주 이용하는 외항사까지 포함할 것인가.
- **커뮤니티 출처 인정 범위** — 어떤 커뮤니티까지 `raw/`의 정식 출처로 인정할 것인가.
- **여행 기록의 포함 여부** — 개인 여행 경험을 정본 지식으로 승격할 것인가. 승격한다면 개인 관찰과 공식 규정을 구분하는 규칙이 별도로 필요하다.
